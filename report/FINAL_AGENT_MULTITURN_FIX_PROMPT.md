## 4. 必须实现的状态与语义契约

### 4.1 条件、引用与执行分离

不要继续用一个 boolean 同时表示“用户说了条件”“修改持久状态”“允许求解”“允许创建草稿”。保留兼容字段可以，但内部需要明确的 typed command/result。

至少独立表达：

- 当前轮的条件操作及其来源。
- 对 Scenario、Pending、建议或分析提案的明确引用。
- 持久记录、临时分析、Preview、Create Draft 等执行指令。
- 目标周、基准排班、状态 revision、当前请求身份。
- 未解决引用、缺槽、冲突和执行阻断原因。

默认语义如下，使用等价实现也可以：

| 用户表达 | 持久有效条件 | 执行 |
|---|---|---|
| 完整条件，或“记住/先记录/先别生成” | 写入 Scenario | 不求解、不创建草稿 |
| 只有员工编号，没有明确修改意图 | 可以更新员工焦点 | 不凭空创建修改或执行授权 |
| 为已有 Pending 补一个明确槽位 | 更新 Pending；完整后转为条件 | 默认只记录 |
| “如果……会怎样/先分析，不要改” | 不自动采纳假设条件 | 在临时分析上下文中评估 |
| “只采纳第一条” | 采纳精确建议的操作 | 默认只记录 |
| “采纳第一条并试排” | 采纳操作 | Preview，不创建 Draft |
| “按当前两个条件重排” | 精确解析当前引用集合 | 从结构化快照创建 Draft |
| 普通“确认/好的” | 不新增执行授权 | 不发布排班 |

“先别生成”只禁止相应执行动作，不能删除同句明确要求保存的条件。“不改/撤销/不是……”必须按分句作用域理解，不能用一个否定词清空整轮。

### 4.2 Scenario、Pending、Focus 和分析提案

以 conversation + target week 为作用域，建立可持久化、可刷新恢复、带版本的状态。最少覆盖：

- 已明确采纳的完整条件，包含稳定 condition ID 或等价原子键及来源。
- 未完成动作及已知槽位、待补槽位、动作身份、来源轮次。
- Focus/Reference，引用条件、员工候选集合、待解冲突或分析提案的身份，不只是复制一份旧 tuple。
- 可引用的建议集合和分析提案，带来源、目标周、基准版本、有效性。
- 未解决冲突/歧义及尚未采纳的操作。

Pending 不能因收到无关只读问题而悄悄丢失，也不能把第二个不完整动作无声覆盖到第一个上。支持必要的多动作暂存，或在无法明确归属时澄清并保留已有状态。显式取消 Pending 后不得复活。

补齐动作的状态转换必须一次完成：添加完整条件、清除对应 Pending、更新 Focus、记录本轮应用结果。补完槽位不自动恢复历史的 CREATE_DRAFT 或 force 授权。

假设问题不能自动写入有效 Scenario，但其结构化分析提案应能被后续明确引用。例如：

```text
如果 E03 周五请假会怎样？
再考虑 E18 周五晚班优先。
把这两个条件记住，先别生成。
```

前面的假设必须保留为有身份的分析提案/分析上下文；最后一句明确采纳时才归约到有效条件。可以复用 typed proposal/suggestion 结构，不必新增无必要的独立系统。不能因为坚持“假设不持久采纳”而无法处理 J/M/N；也不能靠重新解析全部聊天文本偷偷采纳历史。分析元数据的保存不等于改变有效 Scenario revision。

Focus 明确标明引用的是 active condition、pending 还是 proposal；纠正一个假设不能误改有效条件。只读分析也不能清除现有 Pending。

“按这三个重排”只有在三项内容可唯一、完整定位时，才可原子完成“采纳指定提案＋执行”。有效条件和提案混合引用需要去重；不能采纳最近所有假设，不能把已撤销条件从旧提案中复活。提案中不携带历史执行或 force 授权。

### 4.3 精确纠正、撤销和代词解析

- “不是周六，是周日”定位当前明确条件/提案，验证它仍存在且版本有效，原子替换日期，保留员工、班次、类型和其他条件。
- 不使用 employee + type 的宽泛 SET 代替单条纠正。保留 SET 时，限定为用户明确要求整体替换的范围。
- “取消 E06 周四限制”先在明确作用域查找候选：唯一则精确删除；零条或多条给出准确说明/澄清。不要默认为删除请假。
- 区分撤销临时条件、恢复主数据可用性、取消已排班次；撤销一个临时条件不应修改员工档案。
- 员工代词、指示词和“第一条”只对明确且有界的引用集合消解；歧义时询问，不能简单取最后见到的 ID。
- 支持分析中形成的候选员工集合及用户后续选择。技能群体条件在采纳时展开为具体员工快照，并绑定员工数据版本，避免后续静默改变范围。
- 在引用解析前确定/校验目标周。换周不能把旧周 Pending、Focus 或建议默认带入新周；明确“回到刚才那周”可恢复该周状态。统一 read/write 的周解析契约。

### 4.4 冲突检测与后续解决

对整批操作归约后的候选状态检测冲突，不对 REMOVE+ADD 的中间态误报。

至少覆盖同员工同日请假/不可用与 ASSIGN、同日双班 ASSIGN、同槽 ASSIGN 与 UNASSIGN。软偏好与硬不可用区分为无效偏好警告或产品明确的冲突类型，不得把软偏好升级成硬排班要求。

检测需要考虑实际生效的基础可用性、临时条件和已明确授权范围，而非只比较几条文本。

报冲突后保留尚待解决的提案。例如“周二请假 + 周二晚班上”，用户说“取消请假，保留晚班”应一次解决并保留 ASSIGN。未解硬冲突不执行求解/生成，不自动删掉任何一条来制造可行结果。

保护 H01 等不可突破规则。现有允许的规则例外只经现有明确授权流程处理；常规冲突修复不能扩大 force 范围，也不能破坏合法的明确例外路径。

### 4.5 从结构化快照执行与草稿生命周期

建立明确的 EXECUTE_CURRENT_SCENARIO 或等价入口。当前轮提供执行指令，结构化状态提供参数；不要要求最后一句重复 employee/day/shift，也不要从原始历史重新推测执行参数。

执行前至少核对：

- 目标周、被引用条件集合及明确提及的条数；“这两个”可能是明确子集，不能盲目当作整个 Scenario。
- 未完成动作、未解决歧义/冲突；未经用户明确限定，不得静默忽略它们。
- Scenario revision、条件快照/摘要、基准 schedule ID/version、员工数据及影响求解的规则/历史依赖。
- 当前轮生成授权与生成/重排目标。已有正式排班时遵循重排语义和约定的最小改动目标。

当用户引用已有条件而集合无法解析或为空时必须阻断，不能降级成空 changes 的普通生成。用户明确要求无附加条件生成仍是合法的单独路径。

条件计数保留用户要求/提案的语义分组，不简单使用 len(patches)：一条多日请假要求可以展开为多个原子约束，一条交换建议也可以包含多个不可拆分操作。以规范化条件集合、引用身份和分组共同核对用户所说的数量。

最终 Draft 记录可追溯的 source conversation/client message/user message、Scenario revision、执行条件快照或 hash、基准版本。Preview 缓存只能在依赖一致时提升；变化后重新验证/求解，不可把旧 Preview 标成新 revision 的结果。

默认保留每周一个待确认 Draft 的现有策略：有草稿时准确返回 draft_pending，提供现有工作台处理路径，保留已记录条件。本轮不实现自动取消/替换旧草稿。不能因为有旧草稿就禁止所有记录条件、分析、Preview 或建议采纳操作；前后端按动作限制。

明确草稿创建、取消、确认后 Scenario/Pending/Focus/建议的生命周期。至少记录哪个 revision 已用于哪个 Draft；不得失败后清空条件，或重复请求制造第二份草稿。

### 4.6 原子性、幂等和数据库兼容

沿用现有会话租约、client_message_id 去重及排班仓储门禁，并扩展覆盖状态修改。

- 状态命令携带 expected revision、client message ID 和 owner/lease fence。
- 同一轮归约一次提交；相同请求重放返回同一结果，不重复 ADD、REMOVE、采纳建议或增加 revision。
- 非法/过期命令不能部分生效；业务上尚待解决的冲突提案按明确契约保存。
- Preview 结果回写绑定求解时的 revision 和依赖；失去租约或状态已更新的旧 worker 不得覆盖新结果。
- 将 record-only、Scenario 更新及 save_scenario 纳入中断恢复；处理“业务已提交但回复尚未完成”的情况。
- 不持有跨 LLM/Solver 的长数据库事务。短事务提交状态，慢计算使用快照，回写执行条件检查。
- 使用适合实际数据库的行锁/CAS；不要把 SQLite BEGIN IMMEDIATE 当成 MySQL 的同等并发保证。新增迁移兼容当前 SQLite 开发环境和实际部署数据库，旧会话/旧条件有明确兼容或安全失效策略，不猜缺失字段。

## 5. 修复按日偏好执行语义

必须修正 `SchedulingFacts`、目标函数和相关指标，保持 employee 默认偏好与特定日期请求的关系清楚。

- `E18 Thu morning PREFERENCE` 只作用在其明确日期范围。
- 同一员工不同日的不同偏好可以同时生效；交换两条非冲突条件输入顺序，最终有效偏好与目标系数应等价。
- 用户明确整体替换与精确纠正的语义仍有区别。
- 明确默认全周偏好与按日偏好的覆盖/叠加规则，避免双重奖励。
- 偏好满足率分子、分母与真实目标定义一致。偏好是软目标，不保证必然上该班；解释时区分已纳入优化与实际被满足。
- 独立检查目标函数的日期/班次作用范围，并在可控小实例中验证求解行为。不能只断言 requested_changes 被保存或传入 Solver。
- 不为此放宽硬约束，也不把“优先”改成 ASSIGN。

## 6. 建议闭环与前端接线

“读取事实”是生成建议所需步骤，不等于只需返回事实。明确的建议请求必须走完整的分析、候选构建、可引用产物保存和展示路径。

建议结构至少能表达：唯一 suggestion_set_id/suggestion_id、展示序号、来源消息、目标周、基准排班与状态依赖、具体操作、可执行性、可行性状态、改善依据。

- 正文条目、卡片序号、后端存储必须来自同一集合，不能 LLM 编一套序号、后端存另一套。
- 泛化咨询建议可以存在，但明确标为不可直接采纳，不能空 changes 冒充具体调班建议。
- 公平性优化方案应有可验证的前后指标和相同上下文的可行性校验；仅删除最忙员工一个班次不能直接宣称公平性改善。找不到改善时如实说明。
- 前端卡片提交不可变建议身份和动作指令；不能将旧卡片转成“最近第一条”。自然语言“第一条”绑定最近明确展示、符合上下文的集合；过期时明确提示，不跳到其他集合。
- 统一旧建议和 Scenario 建议的 stale/rebase 契约。需要重新验证时明确进行；不要用不完整的类型检查静默允许过期操作。
- 失效策略按依赖类型区分：采纳一个独立条件导致 revision 改变后，另一个纯条件提案可以重新校验并保持原内容；依赖具体排班及公平性指标的建议需要校验完整基准。不能一变 revision 就机械失效所有提案，也不能把重新校验变成偷偷改写建议。
- 采纳建议与手工条件汇入相同归约器，冲突、幂等、撤销、来源追踪一致。
- “采纳并重排”不能在处理中被强制改成 WHAT_IF；当前执行指令必须保留。
- 更新前端类型、请求、状态展示和错误反馈。让用户能看到已记录条件、待补信息及阻断原因，不把内部日志当产品文案。
- 已有 Draft 时，禁止不允许的 Create Draft；允许合法的记录/分析/Preview，不一概禁用所有建议按钮。

## 7. 延迟与错误契约

- ReadTimeout/连接失败不能当成 schema 不兼容而向相同通道再发同样长请求。明确的 strict/schema 不支持可以有一次有预算的兼容重试；分类、次数、原因必须可观测。
- 为 Router、必要的语义提取、回复生成分配独立预算，并遵守整轮剩余预算。不要靠提高所有超时通过验收。
- 明确 ID、已有 Pending 的单槽回答、精确纠正、条件复述和建议引用尽可能在首次 Provider 调用前确定性解决。任意自然语言超出确定性覆盖时，允许带预算的 LLM 解析或澄清；不要伪称全自然语言零 LLM。
- 已明确保存/执行的业务结果不能因为回复润色失败被伪装成业务失败；有真实结果时返回准确的确定性反馈。
- 语义解析失败而无法安全确定意图时，不得用成功文案掩盖失败或猜执行参数。区分解析降级与可选语言润色降级。
- 保留准确的业务错误码，UI 同时呈现明确原因和恢复路径，避免只显示“排班处理失败”。
- 日志记录阶段、耗时、Provider 请求次数、错误分类和降级原因。不要记录密钥、授权头或模型隐藏推理。
- 修正现有要求 ReadTimeout 重试的错误测试契约，并同步调整已与新语义冲突的旧断言；不能删除断言来制造绿色结果。

## 8. 实施过程中的自动化回归

在实施中运行与修改相关的单元/集成测试，最后完成仓库适用的后端测试、前端类型检查/构建/lint 和相关 E2E。按现有依赖及命令运行，失败先定位原因，不盲目重复全量。

新增有意义的行为回归，至少覆盖：

1. 部分槽位跨轮、刷新和服务重启恢复；无关只读插话不丢 Pending；显式取消有效。
2. 记录完整条件不求解；假设分析不自动采纳；后续显式采纳结构化分析提案有效。
3. 纠正只作用于精确条件；撤销作用域、同员工不同日期条件、零/多匹配和旧 Focus。
4. 整批冲突检测与解决；soft preference 不升级 hard assignment；强制授权边界不回归。
5. 最终执行引用集合校验；空条件误执行阻断；条件快照与求解输入、Draft 来源一致。
6. 重复请求、状态提交后回复失败、租约丢失、Preview 过期、并发 revision 检查。
7. 按日偏好顺序不敏感及真实目标系数/求解效果。
8. 建议真实生成、正文与卡片对应、旧卡片不可串批、过期校验、重复采纳及当前执行指令保留。
9. 旧草稿阻断后条件保留；聊天确认不发布；H01 不可突破。
10. ReadTimeout 不发生错误兼容重试；可选回复超时使用真实结果兜底。

固定期望应独立于被测实现，不得用“实际输出等于自身转换后的输出”替代正确性校验。涉及多数据库的并发行为，验证可用数据库上的真实行为；未能运行的数据库类型明确列为未验证。

## 9. 最终必须实际执行：真实 Provider 的完整多轮验收

这是交付条件，不能只写测试脚本而不运行。

### 9.1 新建独立 live 验收入口

当前 `frontend/playwright.config.ts` 强制 `LLM_ENABLED=false`；现有 live agent eval 主要是只读预览，live router eval 是单轮 Router。它们通过不代表本次要求完成。

另设明确的 live 配置/命令，启动修复后的本地后端和前端，连接现有真实 Provider。保留离线回归入口，不把默认 CI 强行变成收费网络测试。

允许采用以下组合：

- 推荐：Playwright 驱动真实浏览器页面，监听真实 HTTP/SSE，并通过只读 API 或测试数据库快照断言状态。
- 也可：A–N 主要通过真实 HTTP/SSE 客户端逐轮执行，再使用真实浏览器覆盖 B 的补槽与刷新、G 的纠正、H 的建议卡片、J 的恢复和旧草稿门禁。
- 浏览器能力确实不可用时，先完成真实 HTTP/SSE 多轮验收，明确报告 UI 未验证及具体阻塞，不能宣称完整浏览器验收通过。

多轮必须经过正常应用入口、持久化、路由、工具和执行链。不得直接调用 reducer/router 注入正确历史来代替最终验收，不得以 trusted action 绕过需要验证的自然语言理解。合法的建议卡片动作是另一个正常入口，应单独测试。

### 9.2 环境与数据隔离

- 为本次 live run 使用独立测试数据库和端口，绑定实际测试构建。记录代码 SHA、未提交变更的 diff 标识、启动配置摘要及测试目标 URL。
- 使用现有可用的模型和 endpoint，不擅自更换 Provider 来掩盖问题。凭据仅从合适的环境配置读取，不打印、不写入报告、不提交。
- `LLM_ENABLED=true` 不足以证明真实调用：记录实际 Provider 请求阶段、模型、脱敏服务标识、成功/失败、耗时。健康检查不计作多轮业务调用证据。
- 不 mock Provider、不伪造返回、不缓存固定答案；允许正常的确定性快速路径，不能为了“每轮都调用 LLM”破坏性能设计。
- 测试集合中必须有连续多轮会话真实经过 LLM 的语义解析或回复链，并有多个不同 Turn 的请求证据；若所有业务 Turn 实际都是确定性路径，再增加自然语言变体多轮用例覆盖实际 LLM 路径，而非只追加独立健康探针。
- 每个 case 使用独立数据库/应用实例，或串行且彻底恢复相同基线；仅新 conversation/browser workspace 不算隔离。明确处理目标周及前后周历史依赖，防止跨周确认互相阻断。
- 固定员工、规则、目标周、已确认排班和可验证的上一周历史。普通成功 case 起始无 pending Draft；旧草稿门禁单独测试。基线准备可以使用测试 fixture，测试开始后不能人工补写待测条件、Pending 或建议。
- 准备可行的 A/B/G 等普通成功实例，H 使用确实存在合法改善机会的基线。不能将全部最终执行都判为 infeasible，然后宣称生成链路通过。

### 9.3 必须逐轮执行的 A–N

下面保留原始对话。一个编号是一条真实用户消息，逐条发送，不合并为一个 prompt。回放原语句时，需要澄清的地方允许插入明确回答，但要记录插入轮和原因，不得删除原始消息或放宽预期。对含糊表达以契约为准：准确澄清是正确行为，凭空猜槽位不是。

CASE A：撤销、替换和最终两个条件。

1. 先帮我看看E06这周是怎么排的。
2. 如果E06周四不上班，会影响什么？先分析，不要改。
3. 那先把E06周四设成不可排，不过先别生成。
4. 等等，这个不要了，E06周四保持原样。
5. 改成让E06周五早班优先。
6. 再加一个，E18周二晚班优先。
7. 你现在重新告诉我，真正有效的两个条件是什么？E06周四还有没有限制？
8. 好，就按现在这两个条件重新排班。

期望：最终仅 E06 Fri morning PREFERENCE、E18 Tue evening PREFERENCE；Thu 旧限制不存在。前七轮无新 Draft，最后使用这两条真实创建关联本轮的新 Draft。

CASE B：完整多轮 Slot Filling。

1. 我想调一个人的排班。
2. E18。
3. 想让他上班。
4. 周四。
5. 晚班。
6. 不过先别生成，你告诉我现在理解我要干嘛。
7. 再加一个条件，E06周五请假。
8. 好，就按这两个要求重新排班。

期望：逐步补齐 E18 Thu evening ASSIGN，再加入 E06 Fri LEAVE；不能要求重述已明确槽位。另以独立运行在补槽中途刷新页面，再继续同一会话，验证数据库恢复。

CASE C：多人条件与不可行诊断。

1. 我想调整三个人，先别生成。
2. E06周四请假。
3. E11周五晚班优先。
4. E18周二不要排。
5. 你先看看这三个条件一起会有什么影响。
6. 如果有问题，具体告诉我哪一天哪个班次缺什么，不要自己删条件。
7. 现在把三个人的条件分别复述一次，一人一行。
8. 如果能满足硬约束，就按这三个条件重新排。

期望：条件不串员工、不丢失；“周二不要排”保存整日不可排语义。可行才生成，否则准确诊断并完整保留条件。

CASE D：技能查询、候选引用与明确选人。

1. 周末能上班的兼职有哪些？
2. 这里面同时会饮品和收银的是谁？
3. 那个同时会饮品和收银的兼职，如果放周六晚班合适吗？
4. 如果有多个，你列出来，我来选。
5. 我选E19。
6. 那刚才那个要求就按E19周六晚班优先来理解，先分析。
7. 再加E15周日请假。
8. 按这两个条件重新排班。

期望：候选员工来自真实主数据；多候选不擅自选人。最终明确引用的 E19 Sat evening PREFERENCE、E15 Sun LEAVE 能进入执行快照，分析提案是否已采纳需准确标明。

CASE E：代词、冲突和解决。

1. 我要调一下E18。
2. E18周二请假。
3. 同时我又想让他周二晚班上。
4. 先别改，你告诉我哪里冲突。
5. 那取消周二请假，保留E18周二晚班上班。
6. 再加E11周四晚班优先。

8. 没有问题的话就重新排班。

期望：明确识别同员工同日冲突；“他”稳定指向 E18；解决后保留 E18 Tue evening ASSIGN、E11 Thu evening PREFERENCE，不复活请假，不丢 ASSIGN。

CASE F：群体条件、可用性恢复与真实不可行。

1. 周日如果所有有manager技能的人都不上班会怎样？
2. 主要会违反哪些规则？

7. 现在重新分析一次是否可行。
8. 如果现在可行，就按照修正后的条件生成草稿。

期望：群体范围有依据，不越权 force；区分允许某个班次与强制安排。只恢复 E02 晚班可能仍缺周日早班 manager，不能预设一定可行。必须以明确的班次级可用性或等价约束精确表示恢复范围，不能把“只允许晚班”扩大成整日可用。只有原句存在实际歧义时才澄清；单纯返回“暂不支持”不能算此能力通过。

CASE G：日期纠正与旧条件消除。

1. 我想让E19周六晚班优先。
2. 你先告诉我你理解的具体条件是什么。

4. 班次还是晚班。

期望：只有 E19 Sun evening PREFERENCE、E15 Sat LEAVE。另补同员工另一天既有偏好，断言纠正不会一并删除它。

CASE H：公平性建议、指定采纳与自定义条件。

1. 你先分析这周员工工作量有没有明显不均衡的。
2. 如果想让工作量公平一点，你给我一个优化方案，先不要执行。

6. 再加我自己的要求：E20周五晚班优先。
7. 所以现在最终准备执行几条？具体是哪几条？
8. 好，按这两条重新排。

期望：确实产生有唯一身份且有具体操作的建议；只采纳用户选中的那一条，另加自定义偏好；新草稿输入与所选建议操作一致。若一个建议包含多个不可拆分原子操作，明确“2项用户要求/若干原子操作”，不能为了条数拆坏操作组。另生成第二批建议后点击第一批卡片，检查不串批和正确过期处理。

CASE I：一出一进与合规检查。

1. 周六早班为什么现在是这些人？
2. 技能覆盖里哪些是重复比较多的？
3. 如果想少动整体排班，谁比较适合从周六早班调整出去？先分析。
4. 我自己提个方案：把E11从周六早班去掉，可不可以？
5. 然后把E19放进周六早班。

7. 再检查工时、连续工作、晚转早。
8. 如果都合法，就按这个一出一进重新排。

期望：对结构化组合提案检查，不只复述原排班；最终引用包含 UNASSIGN E11 Sat morning 和 ASSIGN E19 Sat morning。不得把已移出的人员算进覆盖。

CASE J：刷新、显式记住与后续撤销。

1. 先帮我分析E03本周工作量。
2. 如果E03周五请假会怎样？

期望：明确记住时可采纳先前分析提案，刷新后恢复；最后仅 E18 Fri evening PREFERENCE、E06 Wed morning PREFERENCE。不能靠客户端缓存聊天重新拼出条件。

CASE K：周次定位与执行基准。

1. 10月5号那周是哪一周？
2. 那一周有没有正式排班？
3. 下一周呢？

期望：使用固定测试时钟/明确年份，目标为测试约定的 2026-10-05 周；正确说明已有正式版本时的重排基准，不污染相邻周。另补 UI 换周后单槽回复不能误接旧 Pending。

CASE L：中断话题、建议引用与重新给出最终条件。

期望：解释建议不等于采纳；只读插话不引入无关条件；最终执行明确引用的两个条件，不能把未采纳建议一并执行。

### 9.4 必需的补充 live/恢复检查

- 两个不同日期偏好先后顺序交换，在独立干净场景得到相同有效偏好及目标语义。
- 普通有旧 Draft 的执行明确 draft_pending，条件保持；在独立测试环境通过正常工作台取消该草稿后，重新发起执行能用原条件创建正确草稿。
- 普通聊天“确认”不产生 confirm API 或状态发布；若测试确认流程，仅通过正常工作台按钮并记录调用。
- H01 同日双班不能因“强制/忽略规则”生成可确认非法排班。
- 同 client_message_id 重发不重复提交状态或创建草稿；业务提交后连接断开仍可恢复同一结果。
- 本地服务重启后继续未完成 Pending；跨周回来恢复正确状态。
- 真实 Provider 网络失败必须被准确分类；人为 timeout/断连故障注入可用于补充恢复测试，但与未 mock 的正常 live 结果分开报告。

### 9.5 本轮完成判定与证据

每条用户消息以 conversation_id + client_message_id/turn_id 对应到实际 HTTP/SSE 请求。等待本轮终态、持久化助手回复和前端恢复可输入后，才发送下一条。

禁止以下判定方式：

- 整页出现“草稿/已确认/处理完成”就算成功。
- HTTP 200 就算 SSE 业务成功。
- 固定 sleep 后抓旧回复；强制点击绕过 busy。
- 把已有 v6 卡片算作本轮新草稿。
- `slice(-30000)` 截断 JSON 后当作完整状态快照。
- 将自写正确条件注入数据库或 Router 后声称自然语言多轮通过。

每轮记录：用户原文、消息身份、目标周、实际解析结果、状态前后快照、revision、缺槽/冲突/引用解析结果、执行指令、工具输入输出、错误码、新草稿身份及来源、真实 Provider 调用和分阶段耗时。使用仅限测试环境的只读观测方式，不暴露生产调试接口。

执行通过必须形成完整链条：明确的当前轮执行指令 → 对应状态快照 → 编译后的有效条件 → Solver/Validator → 本轮来源的新 Draft。软偏好检查目标语义与实际满足情况，不能强行断言必定满足。

保留完整、可解析、已脱敏的 JSON/SSE；保存关键截图和浏览器 trace。保留全部失败尝试，重跑写新 run ID，不覆盖失败证据。明确区分产品失败、Provider 失败、验收器失败、未完成和 skip。

首次完整执行 A–N；A/B/E/G/H/J 在独立干净状态至少再运行一次，并加入若干自然语言等价变体，防止只针对固定句子修关键词。修复新失败后重跑受影响用例及必要回归，不无意义重复已验证部分。

报告逐轮 Router、状态归约、工具、Solver、回复生成、服务端总耗时和浏览器总耗时，说明计时范围，避免嵌套阶段重复相加。给出样本数、p50/p95、超时数、Provider 请求数、降级数和所有尝试的结果，不能只统计最终成功轮。

## 10. 交付物与完成标准

交付：

1. 完整实现及必要数据库迁移、前端接线和文档更新。
2. 有意义的单元/集成/E2E 回归及运行结果。
3. 可重复执行的真实 LLM 多轮验收命令、数据基线准备方式、配置说明；不包含密钥。
4. 独立目录下的 live 运行产物，例如 `artifacts/agent-multiturn-live/<run-id>/`，包含完整 transcript、状态快照、请求/执行证据、截图/trace 和汇总。
5. 最终修复报告，列出改动与问题对应关系、真实测试环境/构建身份、A–N 逐项结果、关键条件快照和新 Draft 来源、性能数据、剩余问题及未验证范围。

只有代码检查、行为回归和实际运行的真实 LLM 多轮验收都有证据，才能宣布完成。Provider 凭据、网络或浏览器被阻塞时，准确写明已完成部分与待完成验证；不要声称全部通过，也不要以一个成功草稿代替整套验收。

开始执行：先核对现状，确定最小完整实现路径，然后持续完成修复和验证。
